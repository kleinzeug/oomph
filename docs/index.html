0x01 · The dialog it explains

You know this dialog.

You leave the Mac alone with a few long-running jobs. You come back to the Force Quit window, some processes are gone — and by the time Activity Monitor is open, everything looks fine. Whatever happened, happened while nobody was looking. oomph was looking.

⚠︎
Your system has run out of application memory.

To avoid problems with your computer, quit any applications you are not using.

open Activity Monitor → “looks normal”

0x02 · What it records

A sampler, a log watcher, a report.

A small root daemon takes a measurement every 30 seconds — every 5 while memory gets tight — and keeps listening to the system log for memory kills. The menu-bar app and the oomph command just read what it wrote.

System memory, honestly

Pressure level, app memory, wired, compressed, cache and free — plus swap used, swap size and the number of swapfiles. The same arithmetic Activity Monitor uses.

Every process, by footprint

The 25 biggest processes by physical footprint and the 15 biggest apps with all their helpers added up. As root it sees system daemons too — often the ones that grow.

Whether you were there

Seconds since the last keypress, display on or off, screen locked, who is keeping the Mac awake. The “only when I walk away” pattern becomes a shaded band on a chart.

The free disk, too

Swap lives on your startup disk, so free space is part of your memory. oomph logs it with every sample and warns once below 20 GB.

Agent sessions, grouped

Long-running coding-agent sessions are recorded with their whole process tree and project directory — so “which project blew up?” has an answer.

Incidents, written up

Critical pressure or a burst of jetsam kills opens an incident: one notification, a system-log excerpt, and a self-contained report.html with charts of the minutes leading up to it.

0x03 · Why it happens when you walk away

It's usually your disk, not your RAM.

macOS swap isn't a fixed partition. It grows in 1 GB files on your startup disk — and macOS stops adding them when free space runs low. Here is the chain oomph caught on the machine it was written for:

  1. You step awayYour jobs keep running: builds, containers, agent sessions.
  2. macOS gets busyIdle-only work starts: Spotlight, Siri and Apple Intelligence models, Photos analysis, backups.
  3. The compressor fillsRAM is full, so macOS compresses memory — and then needs to swap.
  4. Swap can't growAnother 1 GB swapfile won't fit: the disk had 9.8 GB free.
  5. Low swapJetsam kills processes in a loop and the Force Quit dialog appears. 60,850 kills in one hour.
≥ 20 GB

Keep that much disk space free and most of these dialogs never happen. Freeing ~50 GB fixed the original problem — oomph exists so the next one comes with evidence instead of guesswork.

0x05 · For long-running agents

Make any Claude session oom-aware.

Coding agents are exactly the workload that tips a Mac over: a build here, a container there, three sub-agents running test suites in parallel. oomph ships a Claude skill that teaches a session to check memory before heavy work, to back off when it's tight and to tell you — and, with several sessions on one Mac, to take turns.

Paste into a Claude Code session — adds the skill to that project
Add the oomph memory skill to this project: run
mkdir -p .claude/skills/oomph && curl -fsSL https://raw.githubusercontent.com/kleinzeug/oomph/main/skills/oomph/SKILL.md -o .claude/skills/oomph/SKILL.md
then read .claude/skills/oomph/SKILL.md and follow it for the rest of this session.

What the session does

Checks oomph check at the start, before builds, test suites, containers or sub-agents, and every 20–30 minutes on long runs. Then:

okcarries on
tightlowers parallelism, starts no new containers or sub-agents, stops what it no longer needs
criticalpauses, stops its own heavy processes, waits for memory to recover, tells you

For every session, once

oomph setup-claude installs the skill and registers the oomph MCP server — memory_check, reserve_memory, release_memory, reservations, incidents — for all sessions. Add --hook and a quiet hook after each shell command tells the model the moment memory turns tight. --remove undoes it.

oomph session shows what the session itself is using — its whole process tree, biggest children first.

Several sessions? They take turns.

Before heavy work a session reserves its peak — oomph run --reserve 6G -- ./gradlew build, or reserve_memory over MCP. oomph grants reservations first-come-first-served: side by side while they fit, one after another when they don't. Nobody starts early, a running job's memory isn't counted twice, and a session that exits gives its share back. Each finished job's real peak is recorded, so the next estimate is better.

0x07 · Good to know

Honest answers.

How do I get it?

Clone the repository and build it — it's free, the source is complete, and there are no binaries. You need macOS 14 or later and Xcode; there's no Xcode project to open, just one script:

git clone https://github.com/kleinzeug/oomph.git
cd oomph && ./build-app.sh
open ~/Applications/oomph.app

Then click the chip → Activate. The README walks through the details.

Why does it ask for my administrator password?

Only root can see the memory footprint of every process, including the system daemons that are often the ones growing — and a logger that should keep running while you're away belongs in launchd, not in a terminal. Activating copies the daemon to a root-owned folder (so nothing user-writable ever runs as root) and starts it. Deactivating removes it again.

Will it fix my memory problems?

No — on purpose. oomph never kills, pauses or throttles anything; it could take down the very job you care about. It tells you what happened. Most of the time the answer turns out to be “free some disk space”, and it warns you about that before it bites.

What does it record, and where does it go?

Memory and disk figures, process names, app names and the working directories of agent sessions — never command-line arguments or file contents. Everything stays in /Library/Logs/oomph on your Mac. No network access, no telemetry.

Can my Claude sessions use it?

Yes — that's what the skill is for. Paste the skill link into a session, or run oomph setup-claude once to give every session the skill and the MCP tools. The commands work even without the background logger; they measure live.

What does it cost?

Nothing. It's MIT-licensed: clone it, build it, change it, ship your fork. If you improve it, a pull request upstream is appreciated.
